# Android emulator playback validation — October 26, 2026

## Environment and scope

Android 15 (API 35), x86_64, KVM acceleration, in a separate `noiser-validation` AVD. No physical
phone was connected. The existing `noiser` AVD was not used or wiped.

The standard standalone Debug APK installed and launched to the normal login/download-location UI.
Playback checks used a separate standalone Debug Mock APK with a temporary validation Activity and
generated, tagged, silent MP3 fixtures. The Activity and fixtures were injected through
`CustomAfterMicrosoftCommonTargets`; they are not included in normal builds or production source.

The harness uses the real `DownloadService.StreamAsync`, progressive buffer, bounded extractor,
ExoPlayer, playback service, MediaSession, MediaController, and playback UI. Only the peer transport
is replaced using the mock client's existing `DownloadToStreamAsyncHandler`. Initial bytes include
the tags and approximately four seconds of audio, followed by throttled chunks. Separate cases
simulate a stall, rejection, and connection closure. No user account or live peer was used.

ANR that initially obscured the notification screenshot. The final captured log contains no fatal
exception or app ANR. See the [timestamped results](2026-10-26-emulator-results.txt).

## Configuration fix discovered

Bundling assemblies in the custom `Debug Mock` configuration exposed a startup failure:
`UnsatisfiedLinkError` for managed Java callbacks before playback. Unlike the exact `Debug`
configuration, this custom configuration defaulted `DebugSymbols` to false. With
`EmbedAssembliesIntoApk=true`, Android selected the non-debug registration path.

`Seeker.csproj` now explicitly sets `DebugSymbols=true` for `Debug Mock`. The generated manifest is
debuggable, the Java callback registration is present, and the rebuilt validation APK starts and
completes the runtime checks above. The ordinary Debug configuration is unchanged by this setting.

## Limits and remaining phone checks

These results validate the exercised Android runtime paths, not the full device acceptance checklist.
The following still need separate validation:

- Audible output, real Bluetooth/headset hardware, incoming calls, and manufacturer-specific behavior.
- Pano Scrobbler or another actual scrobbler, including permissions and detection timing. Publishing
  correct initial session tags passed; recording a real scrobble was not tested.
- Live Soulseek authentication, peer negotiation, TCP disconnects, and real peer queues.
- Artwork rendering/decoding, large or malformed tags on Android, and long-session memory/battery use.
- Notification seek-bar drag gestures. The streamed fixture has unknown duration at the notification
  checkpoint, so its media card has no seek bar. The validated seek used MediaController.
- Full UI selection/download flows, task dismissal, and force-stop/relaunch cache recovery.
